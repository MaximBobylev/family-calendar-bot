# ADR-0001. Аудитория и схема Google OAuth

- Статус: **принято** (2026-10-03), обновлено по итогам ревью

## Контекст

Первые пользователи — автор и его супруга. Если продукт понравится, возможна монетизация: дешёвая подписка или lifetime-лицензия (ADR-0004).
Нужен доступ на запись к календарю, а scope `calendar.events` в Google считается **sensitive**:
- в режиме *Testing* refresh token живёт 7 дней;
- в режиме *In production* без верификации работает с предупреждением «Google hasn't verified this app» и лимитом 100 пользователей (лимит не сбрасывается при удалении пользователей);
- для публичного продукта нужна верификация (домен, privacy policy, демо-видео, проверка Google, несколько недель).

## Решение

1. **Сейчас:** свой Google Cloud проект, OAuth-клиент типа Web, режим **In production без верификации**. Предупреждение на экране согласия устраивает: пользователей двое. Refresh-токены не протухают через 7 дней.
2. **С первого дня — multi-tenant:** все данные привязаны к **внутреннему `user_id`**; `telegram_user_id` — одна из идентичностей пользователя (`ChannelIdentity`), Google-аккаунт — отдельная сущность `ProviderAccount` (ADR-0003). Данные пользователей изолированы.
3. **Регистрация — по allowlist** `telegram_user_id`. Остальным — вежливый отказ. Это защищает квоту Workers AI и лимит в 100 OAuth-пользователей. Права на функции — через entitlements (ADR-0004).
4. Минимальные scopes: `calendar.events` (события во всех календарях с правом записи) и `calendar.calendarlist.readonly` (список календарей, пояс основного календаря, email = id основного календаря). Без полного `calendar` и без `calendar.settings.readonly`.
5. Выданные scopes хранятся на аккаунте; авторизация с `include_granted_scopes=true`, чтобы позже добавлять scopes (Tasks, People) без переподключения.

## Последствия

- `freebusy.query` с этими scopes недоступен — свободное время (US-22) считается по `events.list`.
- Переход к платной версии потребует: домен, privacy policy и ToS, верификацию OAuth, замену allowlist на entitlements. Архитектуру переделывать не придётся.

## Дополнение 2026-10-06: приглашения в дом обходят allowlist (US-90)

- Доступ к боту = allowlist **или** членство в доме. Приглашение — одноразовая ссылка `t.me/<bot>?start=home_<code>` от владельца дома (только он, только из бота): 48 часов, один человек, код в D1 (`household_invites`). Это и есть способ впустить семью, не правя `ALLOWED_TELEGRAM_IDS`.
- Код проверяется **до регистрации**: посторонний с неверным/истёкшим кодом получает «ссылка недействительна» и не становится пользователем. Webhook пропускает `/start home_…` в личном чате без D1 (проверка — в обработчике).
- Вышел из дома, удалён владельцем, дом распущен — доступ по приглашению пропадает сразу (проверка членства на каждом апдейте; для посторонних webhook теперь делает одно чтение D1 — цена спама выросла с нуля до одного SELECT).
- OAuth-лимит в 100 пользователей не тратится: участник без Google ходит в календарь через аккаунт владельца, только в общие календари дома.
- Групповые чаты (US-94): отвечаем людям с доступом (allowlist или дом) и только на обращения к боту; данные — только в чате, привязанном к дому, и только его участникам.
