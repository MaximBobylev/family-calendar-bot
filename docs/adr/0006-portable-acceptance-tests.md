# ADR-0006. Переносимые приёмочные тесты

- Статус: **принято, реализовано** (2026-10-04): `acceptance/` — фейки, раннер, сценарии; запуск `docker compose run --rm acceptance`

## Контекст

Стек на старте — TypeScript на Cloudflare Workers (ADR-0005, [research/hosting-economics.md](../research/hosting-economics.md)). Возможен будущий переезд на Go + VPS. Нужно, чтобы основная ценность тестов — проверка поведения по user stories — пережила переписывание без изменений.

## Решение

Тесты, которые должны пережить смену стека, — это **данные + чёрный ящик**, а не код, импортирующий модули приложения.

### Три переносимых набора

| Набор | Что проверяет | Формат | Кто исполняет |
|---|---|---|---|
| **1. Золотой корпус дат** | детерминированный парсер (ADR-0005, date-rules.md) | JSON/YAML: `{phrase, now, tz, expected \| ambiguous[] \| error}` | маленький адаптер в каждой реализации (TS — vitest, Go — `go test`), читающий тот же файл |
| **2. NLU-корпус** | выбор и качество LLM (ADR-0002): фраза → интент + сырые фрагменты слотов | JSON/YAML: `{text, lang, expected_intent, expected_slots}` + записанные голосовые | отдельный скрипт-бенчмарк против реальных провайдеров; не зависит от стека бота |
| **3. Приёмочные сценарии** | поведение бота целиком по US-xx | YAML-сценарии | внешний раннер против запущенного сервиса через HTTP |

### Приёмочные сценарии — чёрный ящик

Система под тестом (SUT) запускается как обычно (локально `wrangler dev` или staging), но все внешние зависимости указывают на **фейки**:

```
                ┌──────────── Раннер сценариев ────────────┐
                │  читает YAML, управляет фейками и часами  │
                └─────┬───────────────┬───────────────┬─────┘
       Telegram update│     Google push│      часы, cron│
                      ▼               ▼               ▼
                 ┌──────────────────────────────────────┐
                 │                 SUT                   │
                 └───┬───────────┬───────────┬──────────┘
                     ▼           ▼           ▼
             Fake Telegram   Fake Google   Fake STT / LLM
              Bot API        Calendar +    (фикстуры:
             (записывает     OAuth (state  текст → ответ)
              исходящие)     в памяти)
```

**Контракт SUT для тестов** (единственное, что обязана поддержать любая реализация):
- Базовые URL всех внешних API через конфиг: `TELEGRAM_API_BASE`, `GOOGLE_API_BASE`, `GOOGLE_OAUTH_BASE`, `STT_BASE`, `LLM_BASE`.
- Тестовые эндпоинты, включаемые только флагом `TEST_MODE` (в проде отсутствуют):
  - `POST /__test/clock` — установить «сейчас»;
  - `POST /__test/tick` — выполнить всё, что должен был сделать планировщик до текущего «сейчас» (вместо ожидания cron);
  - `POST /__test/hourly` — часовые работы cron (ретеншн, страховка дайджестов);
  - `POST /__test/drain` — дообработать inbox синхронно;
  - `POST /__test/reset` — очистить состояние.
- Детерминированность: при заданных часах и фикстурах ответы бота одинаковы.

**Фейки** — отдельные маленькие HTTP-сервисы (или один), не зависящие от кода бота:
- Fake Telegram: принимает `sendMessage`, `editMessageText`, `answerCallbackQuery`, `getFile` и т.п., записывает их; отдаёт файлы голосовых.
- Fake Google Calendar + OAuth: календари и события в памяти, `events.list` с `syncToken`, `events.watch`, `sendUpdates`, ошибки по сценарию (403, 404, 410, 429, 5xx).
- Fake STT/LLM: возвращает заранее заданный ответ по входу (голосовое → текст, текст → tool call). **Приёмочные тесты не зависят от реальной модели**; качество модели проверяет набор 2.

### Формат сценария (реализованный)

Сценарий — последовательность шагов; ожидания проверяют вызовы фейков, сделанные после предыдущей проверки:

```yaml
- id: start-greets-allowed-user
  story: US-01
  steps:
    - clock: "2026-10-07T07:00:00Z"              # POST /__test/clock
    - telegram: { from: 1001, text: "/start" }   # апдейт в webhook + /__test/drain
    - expect_telegram:                           # ровно эти вызовы Telegram, по порядку
        - { chat_id: 1001, text_contains: ["Google Календарь"], buttons: [...] }
    - expect_no_telegram: true
    - webhook_raw: { body: {...}, secret: null, expect_status: 403 }
```

Шаги для Google, STT и LLM добавляются вместе с соответствующими фейками.

### Пример сценария (целевой, с календарём)

```yaml
id: US-30-ambiguous-weekday
story: US-30
given:
  now: 2026-10-07T10:00:00+03:00        # среда
  user: { tg_id: 1, lang: ru, tz: Europe/Moscow, connected: true, mode: cautious }
  calendars: [{ id: primary, default: true }]
  llm:
    "Поставь встречу на среду в 12":
      intent: create_event
      slots: { start: "на среду в 12" }
when:
  - telegram: { text: "Поставь встречу на среду в 12" }
then:
  - telegram_sent:
      text_contains: ["ср 7 окт", "ср 14 окт"]
      buttons: ["Сегодня, ср 7 окт", "Ср 14 окт", "Отмена"]
  - google_calendar: { events_created: 0 }
when_next:
  - telegram: { callback: "button:Ср 14 окт" }
then_next:
  - google_calendar:
      event_created: { start: 2026-10-14T12:00:00+03:00, end: 2026-10-14T13:00:00+03:00, title: "Встреча" }
  - telegram_sent: { text_contains: ["Как назвать встречу?"] }
```

Проверки — по смыслу, а не по точному тексту (`text_contains`, кнопки, вызовы API), чтобы правка формулировок не ломала тесты. Тексты i18n проверяются отдельно.

### Правила

- Каждый AC из user-stories.md, который можно проверить снаружи, получает хотя бы один сценарий; сценарий ссылается на `story`.
- Раннер и фейки живут в отдельной директории (`acceptance/`) и **не импортируют** код приложения.
- Раннер на старте — TypeScript (один тулчейн), но сценарии и фейки — по HTTP, поэтому раннер и фейки переиспользуются против Go-версии без изменений.
- Те же сценарии запускаются против staging (с фейками) в CI.
- Юнит-тесты внутри реализации допустимы и полезны, но они **не** переносятся — переносится только то, что выше.

## Последствия

- Чуть больше работы на старте: фейки Telegram и Google, тестовые эндпоинты, внедряемые часы.
- Внедряемые часы и конфигурируемые URL — требование к архитектуре с первого дня (ADR-0003: никаких прямых `Date.now()` и захардкоженных адресов).
- Переход на Go = новая реализация SUT + адаптер для золотого корпуса дат; раннер, фейки и сценарии остаются.
