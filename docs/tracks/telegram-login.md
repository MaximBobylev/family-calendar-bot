# Трек: подтверждение Telegram-аккаунта при подключении Google (tech-debt #1, полное решение)

- Статус: **в работе** — этап 1 (PKCE + привязка к браузеру) сделан 2026-10-05; этапы 0, 2–4 ждут решения по домену. Обязателен **до публичной беты (R3)** — пока ботом пользуются двое из allowlist, хватает минимальной защиты.
- Сейчас сделано (минимум): ссылка «Подключить» открывает страницу «Вы подключаете Google Календарь к Telegram-аккаунту Имя (@username). Если это не вы — закройте страницу»; к Google — только кнопкой с этой страницы (POST + CSRF-cookie). Защита держится на внимательности человека.
- Цель трека: **сервер сам проверяет**, что ссылку в браузере открыл тот же человек, чей Telegram-аккаунт получит календарь, и что код от Google вернулся в тот же браузер. Без надежды на то, что кто-то прочитает страницу.

## Угрозы

| # | Сценарий | Последствие | Сейчас | После трека |
|---|---|---|---|---|
| A1 | Злоумышленник просит у бота ссылку «Подключить» **для своего** Telegram и присылает её жертве («подключи календарь к нашему боту для записи»). Жертва соглашается в Google | Календарь жертвы привязан к Telegram злоумышленника: он читает и меняет её события через бота | Страница называет чужое имя — жертва может не заметить | Невозможно: подпись Telegram показывает, что ссылку открыл другой человек |
| A2 | Пользователь сам переслал свою ссылку (по ошибке, в семейный чат), её открыл другой | Как A1, только без злого умысла | Как A1 | Невозможно (см. A1) |
| A3 | Ссылка утекла: история браузера, скриншот, превью ссылок в мессенджерах | Как A1, если ссылка ещё жива (10 мин) | Одноразовость и TTL; превью не POST-ит, поэтому до Google не доходит | В ссылке нет ничего, что даёт доступ без входа через Telegram |
| A4 | Обратная подмена (login CSRF): злоумышленник подсовывает жертве свой `callback?code=…&state=…` | Telegram жертвы получает **Google злоумышленника**: события жертвы, созданные через бота, уходят к нему | ✅ закрыто (этап 1): cookie `oauth_bind` ставится при переходе к Google, callback без неё — 403 | Callback принимается только в браузере, начавшем вход (cookie) |
| A5 | Перехват `code` (логи прокси, Referer, вредоносное расширение) | Обмен кода на токены от имени нашего приложения | ✅ закрыто (этап 1): PKCE S256 + `client_secret` | PKCE: без `code_verifier`, который знает только наш сервер, код бесполезен |

Вне трека: компрометация самого Telegram-аккаунта (тогда злоумышленник и так пишет боту от имени жертвы), фишинговый клон бота с похожим именем.

| Вариант | Как подтверждает, кто открыл | UX | Требования | Оценка |

Подпись — тот же алгоритм, что у Login Widget | Одно нажатие в чате; при первом входе на домен Telegram спрашивает «Войти на … как Имя?» | Домен, привязанный к боту в @BotFather (`/setdomain`); URL кнопки — на этом домене | **Рекомендуется**: родной механизм Telegram для «войти на сайт из кнопки», без JS и без лишних страниц. Пересланная кнопка авторизует того, кто её нажал (у `login_url` даже есть `forward_text` для пересылки) |
| **2. Telegram Login Widget** на странице `/connect` | Виджет (iframe oauth.telegram.org) — вход в Telegram в браузере, подписанные данные пользователя | Ввод телефона и подтверждение в Telegram при первом входе в этом браузере — заметное трение | `/setdomain`; внешний JS с telegram.org (ослабляет CSP) | Запасной путь: вход с сайта без чата (будущий лендинг, десктоп) |
| **3. | 4. Подтверждение в боте после согласия («Подключить ivan@gmail.com? Да/Нет») | Сообщение уходит владельцу ссылки | +1 нажатие после Google | — | **Не защищает от A1**: подтверждать будет злоумышленник. Не берём |

**Решение:** вариант 1 (`login_url`) — основной; плюс привязка к браузеру (cookie) и PKCE — они нужны при любом варианте. Вариант 2 — когда появится вход с сайта. Страница из варианта 0 остаётся как экран «Подключаете к **проверенному** аккаунту …» без поля для ошибки человека (можно убрать, решим по UX).

## Целевой поток

```
Бот: [Подключить Google Календарь]   ← кнопка login_url: https://<домен>/oauth/google/start?t=<ticket>
  │  нажатие → (первый раз) Telegram: «Войти на <домен> как Иван?» → Да
  ▼
GET /oauth/google/start?t=<ticket>&id=…&first_name=…&username=…&auth_date=…&hash=…
  1. проверить hash (HMAC-SHA256, ключ = SHA256(bot_token)) и свежесть auth_date (≤ 5 мин)
  2. ticket (одноразовый, 10 мин) выдан тому же Telegram id?  нет → страница «Эта кнопка для другого аккаунта.
     Откройте бота у себя и нажмите «Подключить»» (без раскрытия чужого имени), в журнал — попытку
  3. создать oauth_state: user_id, code_verifier (зашифрован), browser_binding = SHA256(cookie)
  4. Set-Cookie: oauth_bind=<random>; HttpOnly; Secure; SameSite=Lax; Path=/oauth/google; Max-Age=600
  5. 303 → Google consent (state, code_challenge=S256(verifier), prompt=consent, access_type=offline)
  ▼
GET /oauth/google/callback?code&state
  6. state одноразовый, не истёк;  SHA256(cookie oauth_bind) == browser_binding?  нет → 403 «Начните из бота заново»
  7. обмен code + code_verifier → токены; дальше как сейчас (saveGoogleAccount, сообщение в бот)
  8. удалить cookie
```

Почему `SameSite=Lax`, а не `Strict`: возврат с Google — межсайтовая навигация верхнего уровня (GET), `Strict` cookie не отправит. `Lax` на GET-навигацию отправляет, а для A4 этого достаточно: у злоумышленника нет cookie жертвы, а у жертвы нет `browser_binding` его state.

Тикет вместо state в кнопке: state для Google создаётся только после проверки подписи; тикет без подписи Telegram бесполезен (A3).

## Проверка подписей (чистые функции, переносимые тесты)

| Источник | Строка проверки | Ключ |
|---|---|---|
| Login URL / Login Widget | все поля, кроме `hash`, отсортированные по ключу, `key=value` через `\n` | `SHA256(bot_token)` |
| Mini App `initData` (на будущее) | то же по полям initData | `HMAC_SHA256(key="WebAppData", msg=bot_token)` |

`hash = hex(HMAC_SHA256(key, data_check_string))`, сравнение — за постоянное время (`timingSafeEqual` уже есть в `src/admin.ts`). `auth_date` — секунды Unix; старше 5 минут или из будущего (> 1 мин) — отказ. Векторы — в `testdata/telegram-auth/*.yaml` (ADR-0006: Go-реализация сверяется с тем же файлом): валидный, изменённое поле, чужой токен, просроченный `auth_date`, поле с юникодом и пустым `username`.

## Приёмочные сценарии (`acceptance/scenarios/02-google-connect.yaml` и новый `18-telegram-login.yaml`)

- `connect-login-url-happy-path` — нажатие своей кнопкой → Google → «Подключено»; в state был `code_challenge`, обмен — с верным `code_verifier`.
- `connect-forwarded-button-other-user` — кнопку пользователя 1001 нажимает 1002 → страница «кнопка для другого аккаунта», state не создан, Google не вызывается.
- `connect-tampered-signature` / `connect-expired-auth-date` / `connect-ticket-reused` / `connect-ticket-expired` → отказ, понятная страница.
- `callback-without-binding-cookie` — callback с верным state, но без cookie (A4) → 403, аккаунт не привязан.
- `callback-wrong-verifier` — фейк Google отвергает обмен без верного verifier → «не удалось подключить».
- `connect-flag-off-legacy-button` — флаг выключен → прежняя кнопка и промежуточная страница работают.
- Юнит: векторы подписи; S256 challenge по вектору из RFC 7636 (Appendix B).

## Открытые вопросы

1. **Домен.** Свой домен (и на нём — бот, OAuth redirect URI, страницы privacy/terms для верификации Google) или временно `*.workers.dev`? От этого зависит этап 0; redirect URI в Google Console придётся поменять при переезде.
2. **Промежуточная страница** после проверки подписи: убрать (на одно нажатие меньше) или оставить как «Подключаете к Иван (@ivan)» для спокойствия? Предлагаю убрать: проверка уже сделана сервером.
3. **Нажатие чужой кнопки** (A2): молча отказать или ещё и уведомить владельца кнопки («Кто-то другой нажал вашу ссылку подключения»)? Предлагаю уведомлять — дёшево и полезно для A1.
4. **`request_write_access`** — не просим: бот и так пишет пользователю в личке.

## Риски

- Поведение `login_url` и браузера Telegram отличается по клиентам (особенно Telegram Desktop и Web) — нужен ручной прогон на каждом; флаг позволяет откатиться.
- Google может показать `disallowed_useragent`, если какой-то клиент откроет страницу во встроенном WebView, а не в системном браузере/вкладке — сейчас на мобильном работает; проверить остальные.
- Пользователь с запретом cookie в браузере не пройдёт привязку к браузеру — понятная страница «включите cookie или откройте в другом браузере».
- Смена домена ломает уже выданные кнопки (живут 10 минут — несущественно) и требует нового `/setdomain`.
