# Может ли DeepSeek разрешать даты без нашей грамматики (2026-10-08)

> **Раунд 2** (тот же день, ниже): доработанная схема B — **99,1%** на корпусе point+range, 0,23% молча неверных, 16/17 на отложенном наборе; та же структура внутри вызова интента (C) — 99,6% на point. Структура `when` подключена в бот вторым мнением.

Замер к шагу 4 [архитектурного ревью парсера дат](date-parser-architecture-review.md): «LLM возвращает маленькую структуру, резолвит наш код». Владелец разрешил потратить баланс DeepSeek на этот замер. Модель — `deepseek-flash` (thinking выключен, `temperature: 0`, ответ через вызов функции). Скрипт — `scripts/eval-llm-dates.ts`, сырые ответы — `reports/llm-dates/*.json` (в git не попадают).

## Метод

- **Вход модели** (одинаковый в A и B): фрагмент, `kind`, «сейчас» с днём недели, пояс — как в корпусе (`testdata/dates/README.md`).
- **A**: системный промпт ≈ 3 500 токенов — сжатые правила `docs/date-rules.md` (правило часа, прошедшее время, день недели и «следующая», даты без года, «через N», ночь после дня, части суток, особые случаи point, периоды, интервалы, пояса, что не разбирается, сдвиги/длительности/повторения). Ответ — функция `result`: `result_type` (value / ambiguous / error), `values[]` в формате корпуса, `error`.
- **B**: системный промпт ≈ 2 700 токенов — описание полей структуры с примерами, без правил разрешения («числа копируй как сказано»). Ответ — функция `structure` (схема ниже); код переводит её в AST грамматики (`Ast` из `src/dates/point.ts`) и разрешает тем же `resolvePointOrRange`, что и парсер. Поэтому правила часа, прошлого, вариантов, поясов в B — наши, модель только «читает». Виды `shift`/`duration`/`recurrence` в B не покрыты (в выборке 20 кейсов — помечены «не покрыто», в доли B не входят).
- **Оценка** — сравнение с `expect` корпуса в каноническом JSON. Для ожидаемых вариантов: *exact* — тот же список в том же порядке; *first* — первый вариант модели = первому ожидаемому; *any* — первый вариант (или единственное значение) модели есть среди ожидаемых. Ожидаемая ошибка засчитывается только той же ошибкой. Решающая метрика (порог 90%) — *any*.
- **Выборка** — 300 кейсов, стратифицированная, `--seed 7`: 90 из `16-now-variety.yaml` (point/range, все шесть «сейчас»), 190 point/range из файлов 01–15 пропорционально размеру, 20 shift/duration/recurrence. Обе схемы — на одних и тех же кейсах, concurrency 3.
- **Правило решения** (задано лидом): режим ≥ 90% *any* на выборке → прогон на всём корпусе. Прошёл только B → B прогнан на всех 852 point/range; A — нет.
- **Отложенный набор** — `testdata/dates/holdout-tricky.yaml`, 17 фраз вне корпуса, восстановленных по ревью и `testdata/extract/cases.yaml` (исходный список ревьюера не сохранился). Где правила молчат — `status: proposed`. Корпусный тест файлы `holdout-*` не читает.

### Схема B (сокращённо)

```
unparseable?: true                  — расплывчато, срок («до пятницы»), незнакомое слово/пояс, «не выражается полями»
day?: {type: relative_days, days} | {type: relative_months, months}
    | {type: weekday, weekday: MO..SU, which: none|this|next|next_week|plus_week}
    | {type: date, day, month?, year?, weekday?}
time?: {hour, minute, meridiem?: am|pm|day|night, special?: noon|midnight}   — час как сказан
part_of_day?: morning|day|afternoon|late_afternoon|evening|night
in_minutes?: N                      — «через час», «через сутки» без часа
interval?: {start: time, end: time};  alt_time?: time («в 9-15»)
date_range?: {from: {day, month?, year?}, to: {...}}
period?: {type: week|weekend|month|next_days|segment, which?: this|next|auto, month?, days?, unit?, segment?: begin|middle|end}
by?: true                           — «к пятнице», «by Friday», «к 18»
timezone?: IANA                     — «по Киеву» → Europe/Kyiv
```

Отображение в AST — `astOfB` в скрипте; «на этой неделе» при `kind=point` → `vagueWeek`, день недели + «на следующей неделе» → `nextWeek` — как делает грамматика. Час > 24 / минуты > 59 → `invalid_time` (как `checkTime`).

### Промпт A (сокращённо)

> You resolve a date/time fragment for a calendar bot into the FINAL value, following the rules exactly… HOURS without am/pm: 1–6 → 13:00–18:00; 7–11 → 07–11; 12 → 12:00 … TIME WITHOUT A DAY: still ahead → today. Morning hour 7–12 passed but +12h ahead → ambiguous [today evening, tomorrow morning] … WEEKDAY: … «в следующую пятницу» → ALWAYS ambiguous [nearest, +7] … NIGHT: «завтра ночью» → the night AFTER that day … POINT SPECIALS: «на неделе» → ONE day: middle of the remaining weekdays … RANGES … INTERVALS … TIME ZONES … UNPARSEABLE …

Полный текст — `SYSTEM_A` / `SYSTEM_B` в `scripts/eval-llm-dates.ts`.

## Типичные ошибки

**A (выборка, 50 промахов):**
- Часть суток без часа → `unparseable` или придуманный час: «завтра утром» в 23:30, «tomorrow evening», «ближе к вечеру», «под вечер», «на завтрашний вечер» → `unparseable`; «tonight», «сегодня вечером» → 18:00; «завтра к вечеру» → 18:00; «в пятницу с утра» → 09:00. Самый массовый класс (≈ 20).
- Правило часа и прошедшего времени: «в 12» и «в 11» в 10:00 → лишние варианты; «в 9:30», «в пять минут восьмого» → только вечер без «завтра утром»; «7 октября в 9» в тот же день → 2027 год вместо 21:00; «в 9 по Москве» → 08:00 сегодня (в прошлом).
- Календарная арифметика: «в понедельник в 10» 31.12 → 5 января (вторник); «через день» 24.10 → 26.10; «на неделю вперёд» → 8 дней.
- Периоды: «в начале месяца» → `{from: 2026-10-12, to: 2026-10-10}` (конец раньше начала); «late this week» с сегодня; «до конца недели» в воскресенье → `unparseable`.

**B (весь корпус, 32 промаха):**
- Пробелы промпта, не модели (≈ 20): «до конца недели», «rest of the week», «until the end of the month» → `unparseable` или «конец месяца» (в промпте «до пятницы» — срок, а «до конца недели» в списке недели — противоречие); опечатки «сегоня», «во вторнек», «в четвёрг» (промпту не дали таблицу `TYPOS`); «через пару дней», «in a couple of days», «через денёк»; «by tomorrow», «by Wednesday»; «at night»; `empty` и `invalid_time` (схеме нечем их выразить).
- Ошибки модели (молча неверные, 10): «через сутки» / «через двое суток» → `relative_days` вместо `in_minutes` (дата вместо момента, 5 кейсов, хотя пример в промпте был); «на 11», «на 3» → число месяца вместо часа; «до конца месяца» → `segment end`; «на неделе вечером» → «вечером» без недели; «в 9-15 вечера» → лишний вариант-интервал.

## Стоимость и задержка

- Один вызов: A ≈ 3,6 тыс. токенов на вход / 70 на выход, B ≈ 2,8 тыс. / 55. Системный промпт попадает в кеш DeepSeek в 92–93% токенов входа, поэтому платим в основном за выход: A ≈ $0,00009–0,00018, B ≈ $0,00007–0,00014 за вызов (10 000 разборов — $0,7–1,4).
- Задержка: p50 ≈ 1,1 с, p95 ≈ 1,4 с — **дополнительный последовательный вызов** к уже существующему разбору интента (наш парсер — микросекунды). В проде B можно встроить в тот же вызов интента (поле структуры вместо строки `start`) — тогда задержка не растёт.
- Весь замер: 1 466 вызовов (580 выборка + 852 весь корпус + 34 отложенный набор), ≈ $0,11–0,23. 0 сбоев, 0 ответов 429.

## Сравнение с нашим парсером и рекомендация

- На корпусе наш парсер — 100%, но корпус писали под него; честное сравнение — отложенный набор: у парсера 1 молча неверный ответ из 17, остальное — верно или переспрос; B — 4 молча неверных (2 из-за схемы), A — 3.
- B даёт 96% на корпусе без единой строки грамматики, и почти все промахи — пробелы промпта/схемы, которые лечатся текстом: таблица опечаток, «до конца недели/месяца», «пара», «by + день», жёстче пример «через сутки». Порядок величины после правок — 98–99%, но это нужно перемерить.
- A не годится как основной путь: 85% на корпусе и 29 уверенно неверных из 300, причём ошибается в календарной арифметике, а не только в правилах.

**Решение для шага 4** (предлагаю, решает владелец):
1. **Грамматика — основной путь** (мгновенно, бесплатно, без сети, 100% на известных формулировках).
2. **B — второй путь** вместо сырого `start` от LLM в `startCheck`: когда грамматика даёт `unparseable` или извлечение `unsure`, а также для пересланного текста и фото (шаг 5). Структура возвращается тем же вызовом интента.
3. **Перед этим доработать схему B:** поле `unsupported` («не выражается») с явной инструкцией не втискивать; `nth_weekday` (первый/второй/последний <день> <месяца>) и `offset_days` от даты («за день до») — их резолвит наш код; `alternatives[]` для «завтра или послезавтра»; таблица опечаток и правила «до конца …», «пара», «by + день» в промпт; `empty` / `invalid_time` — кодом до вызова. Перемерить на корпусе и отложенном наборе.
4. Переключать основной путь на B (грамматика — запасной при исчерпании квоты и без LLM) — только если после правок B ≥ 99% на корпусе **и** лучше грамматики на наборе реальных анонимизированных фраз (шаг 3, после живого использования).

### Что изменено в схеме и промпте

Схема и правила вынесены в прод-код — `src/nlu/date-structure.ts` (один текст и для замера, и для поля `when` у `create_event`); разбор и разрешение — `src/dates/structured.ts` (чистый модуль, юнит-тесты `test/structured.test.ts`).
- `error`: `unparseable` | **`unsupported`** («не выражается полями» — с прямым запретом втискивать: «после отпуска», «за два дня до Пасхи») | **`empty`** | **`invalid_time`** (и правило «копируй числа как сказаны»: час 26 → наш код отвечает `invalid_time`).
- День: **`nth_weekday`** (`n` 1…5 или −1, день недели, месяц — нет месяца = этот), **`last_day`**; у любого дня — **`offset_days`** («за два дня до 20 декабря», «N-й с конца» = `last_day` + сдвиг). Месяц для n-го дня недели без года — ближайший, где дата не в прошлом.
- **`alternatives[]`** — несколько трактовок, только когда фраза сама называет варианты («в среду или в четверг в 10»); код разрешает каждую и склеивает варианты без повторов.
- Промпт: закрытая таблица опечаток (из `TYPOS` в `lexicon.ts`), «ё = е»; «пара», «денёк», «часик»; «by/к + день»; «до конца недели/месяца» = остаток периода, «к концу недели» / «by the end of the week» = срок (`unparseable`); «сутки» — всегда `in_minutes` (24 реальных часа), кроме «через сутки в 10»; «на 4» — час, «на 4-е» — число; `alt_time` только без части суток («в 8-15 вечера» = 20:15); период + часть суток.
- Проверка строгая: незнакомое поле (в т.ч. `offset_days` не в том месте — так модель ответила в первом прогоне на «предпоследний день месяца»), неверный enum, нецелое или вне диапазона число — **вся структура отбрасывается**. `null` = поле не задано; строка JSON вместо объекта разбирается.

**Переобучение.** В правилах 136 примеров в «ёлочках»; 77 из них дословно есть в корпусе (в промпте раунда 1 — 74 из 109). Новых дословных совпадений с корпусом — 4 («by the end of the week», «после завтра», «в последний день месяца», «до конца месяца»), остальные новые примеры нарочно взяты не из корпуса («через пару недель», «в 8-15 вечера», «во вторую субботу декабря» и т.п.). С отложенным набором — **0 совпадений** (одно, «в ночь с пятницы на субботу», нашлось при проверке и заменено на «со среды на четверг» до финального прогона). Значит, рост на корпусе отчасти — «подгонка правилами» под известные классы промахов; честнее мерило — отложенный набор и реальные фразы (tech-debt #26, #27).
