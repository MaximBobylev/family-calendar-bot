# Push и синхронизация Google Calendar: требования и решения (2026-10-06)

Исследование к ADR-0005 §2 и US-72 («Исследовать: требования Google к адресу push-канала, срок жизни каналов, как отличать эхо своих правок»). Источники — документация Google, прочитана 2026-10-06:
[Push notifications](https://developers.google.com/calendar/api/guides/push), [Synchronize resources efficiently](https://developers.google.com/calendar/api/guides/sync), [events.watch](https://developers.google.com/calendar/api/v3/reference/events/watch), [events.list](https://developers.google.com/calendar/api/v3/reference/events/list). Живых вызовов не было.

## Что требует Google

**Адрес канала (`address`)**
- Только HTTPS с **действительным сертификатом**: не самоподписанный, от доверенного CA, не отозван, subject совпадает с именем хоста. Иначе уведомления не доставляются.
- **Подтверждения владения доменом в текущей документации нет.** Раньше (до ~2019) для push требовалась верификация домена в Search Console и регистрация в консоли API — в нынешних руководствах Calendar API этого раздела нет; упоминаются только HTTPS и сертификат.
- Вывод для нас: `https://<воркер>.workers.dev/google/push` формально подходит (сертификат Cloudflare, имя совпадает). **Проверить живьём** первым же деплоем с `GOOGLE_PUSH_ENABLED=true`: `events.watch` вернёт 200 и `resourceId`, затем придёт уведомление `sync` (видно в логах: `{"event":"google_push","state":"sync"}`). Если Google откажет (ошибка `push.webhookUrlUnauthorized` или подобная) — остаёмся на опросе (флаг выключить) и переходим на свой домен (он нужен и к R3 — верификация OAuth).

**`events.watch`** — `POST /calendars/{calendarId}/events/watch`, тело: `id` (наш, ≤ 64 символов; UUID), `type: "web_hook"`, `address`, `token` (≤ 256 символов — приходит обратно в `X-Goog-Channel-Token`), `expiration` (мс) или `params.ttl` (секунды). Ответ — `resourceId` (нужен для остановки) и `expiration`.
- **Срок канала:** `params.ttl` по умолчанию 604 800 с (7 дней); максимум в документации не назван, Google может дать меньше запрошенного — берём `expiration` из ответа.
- **Автопродления нет:** до истечения открыть новый канал (`watch`), старый остановить. Каналы перекрываются — уведомление может прийти по обоим.

**Уведомление** — `POST` на адрес, тела нет, заголовки:
- `X-Goog-Channel-ID` — наш id канала; `X-Goog-Channel-Token` — наш секрет (если задан); `X-Goog-Resource-ID`, `X-Goog-Resource-URI`;
- `X-Goog-Resource-State`: `sync` — канал открыт (сообщение № 1), `exists` — что-то изменилось, `not_exists` — ресурс удалён;
- `X-Goog-Message-Number`, иногда `X-Goog-Channel-Expiration`.
- Ответ 200/201/202/204/102 — успех. На 500/502/503/504 Google повторяет с backoff, прочие коды — сбой доставки (не повторяет).
- Уведомление не говорит, *что* изменилось: нужно прочитать изменения (`events.list` с `syncToken`).

**`channels.stop`** — `POST /channels/stop`, тело `{id, resourceId}`. Остановить может только тот же пользователь (тот же OAuth-клиент), что открыл канал.

**Синхронизация (`events.list`)**
- Полная синхронизация отдаёт `nextSyncToken` на **последней странице** (на промежуточных — `nextPageToken`).
- С `syncToken` нельзя: `iCalUID`, `orderBy`, `privateExtendedProperty`, `q`, `sharedExtendedProperty`, `timeMin`, `timeMax`, `updatedMin`. Остальные параметры — те же, что в полной (у нас `singleEvents=true`).
- Ограничить полную синхронизацию датами можно («you may want to limit your full sync to only a certain date range») — пример Google использует `timeMin`.
- Инкрементальный ответ **всегда содержит удалённые** события (`status: "cancelled"`).
- Токен просрочен — **410 Gone**: стереть локальное состояние и сделать полную синхронизацию заново.

## Как сделано у нас (`src/sync/*`, миграция 0012)

- **Одна подписка на календарь провайдера** (`calendar_sync`, ключ — id календаря у Google), а не на аккаунт: общий календарь семьи синхронизируется один раз, читается токеном одного «владельца» (первый подключивший, с правом записи). Отключился владелец — его каналы останавливаются его токеном до отзыва, синк сразу переходит к другому пользователю.
- **Webhook `/google/push`**: канал ищется по `X-Goog-Channel-ID`, секрет сравнивается за постоянное время (403 — чужой, 404 — неизвестный канал), `sync` — 200 без действий; иначе — задача `cal_push` в `scheduled_jobs` и сразу в очередь. Синк — в потребителе очереди, не в запросе. Пачка push, пока задача ещё ждёт, — одна задача.
- **Синк**: инкрементально по `syncToken`; нет токена или 410 — полная синхронизация окна **−1 / +60 дней** (`timeMin`/`timeMax`); если Google не выдаст токен для окна (не проверено живьём) — следующий синк снова полный, со сверкой — работает, только дороже. При полной пересинхронизации снимки в окне, которых нет в ответе, считаются удалёнными. Первая синхронизация только запоминает (ничего не рассылает).
- **Снимки событий** (`event_snapshots`) — «было» для уведомления «Перенесено (было …)» и время для напоминаний US-71.
- **Эхо своих правок**: после записи бот сам кладёт в снимок ответ Google (с новым etag) и сразу рассылает уведомление в другие чаты; push про эту же правку приносит событие с тем же etag — изменений нет. **etag**, а не `updated`: etag меняется при любой правке и однозначно совпадает с ответом на нашу запись; `updated` — время, которое может совпасть у двух быстрых правок. Изменения экземпляров серии, которую бот менял целиком (запись — в мастер-событие), приписываются боту по журналу `bot_writes` (10 минут).
- **Продление**: канал просим на 7 дней; задача `watch_renew` за сутки до конца открывает новый и останавливает старый; плановая сверка тоже продлевает, если до конца меньше суток.
- **Сверка-страховка**: с живым каналом плановый синк — раз в сутки (ловит потерянные push, двигает горизонт напоминаний).
- **Без push** (`GOOGLE_PUSH_ENABLED=false` или `watch` не принят): тот же синк по расписанию — раз в 5 минут для календарей с изменениями за последние сутки, иначе раз в 15 минут.

## Открытые вопросы

- Живая проверка `watch` на `workers.dev` (см. выше) и выдача `nextSyncToken` при полной синхронизации с `timeMax`.
- Лимиты: квота Calendar API — 1 000 000 запросов/сутки на проект; опрос 3 календарей раз в 5–15 минут — сотни запросов в сутки, не проблема.
- Workers Free: ограничение числа запросов к D1 на вызов — синк пишет снимки пачкой (`json_each`, один запрос на 100 событий), но очередь отдаёт до 10 задач в одном вызове (tech-debt #20).
